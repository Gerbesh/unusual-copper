# Предметные трубы и физическое хранение

Реализованный этап UC-07, 2026-10-15. Трубы работают со стандартными Forge `IItemHandler` в загруженных чанках. SSN Bridge остаётся отдельной будущей интеграцией.

## Настройка фабрики

1. Создайте предметные трубы (8 штук из 6 меди и 2 железных самородков) и селектор граней (медь, железный слиток, редстоун).
2. Соедините инвентари трубами. `Авто` соединяет трубы и распознаёт входы/выходы Unusual Copper. Обычный сундук или бочка в этом режиме принимают предметы; извлечение включите явно на обращённой к ним грани трубы.
3. ПКМ селектором по грани переключает её роль. У машины можно назначить боковой предметный вход, чтобы не закрывать небо насытителю.
4. ПКМ по трубе открывает её настройки. Выберите грань; добавьте до восьми шаблонов кликом предметом на курсоре или Shift-кликом из инвентаря. ПКМ по шаблону очищает его. Шаблон не расходует и не выдаёт физические предметы.
5. Выберите белый/чёрный список, совпадение всех данных или только типа предмета. Теги добавляются по идентификатору, например `forge:ingots/copper`; до восьми тегов на грань. Предметные шаблоны и теги объединяются условием «или». Пустой список разрешает всё.

Более высокий приоритет маршрута обслуживается первым; среди равных действует round-robin. `Ниже` начинает волну пополнения при запасе меньше порога, `До` завершает её на максимуме. 0 в нижнем пороге включает постоянное пополнение; `*` в максимуме снимает предел. Запас считается отдельно для каждого варианта предмета с его данными. `Резерв` оставляет заданное количество в источнике.

По умолчанию одна труба пропускает не более восьми предметов за пять тиков. Узкий участок не умножает пропускную способность от нескольких источников. Сервер ограничивает число попыток передачи и посещений узлов при перестроении графа. Граф хранит позиции и ограниченный кеш маршрутов; предметы остаются в сохраняемом буфере трубы, а не в графе.

## Отказ, выгрузка и восстановление

Сначала проверяется реальная возможность вставки, затем извлечение. Каждый фактически извлечённый стек попадает в буфер источника. Если приёмник отказал или принял меньше после симуляции, остаток сохраняется и ожидает нового маршрута. Ошибочный ответ handler с другим предметом переводит груз в остановленный буфер; физически полученные стеки не отбрасываются.

Shift+ПКМ пустой рукой возвращает доступный груз владельцу, сохраняя остаток при заполненном инвентаре. При разрушении трубы груз упаковывается в предмет «Сохранённый груз». ПКМ этим предметом выдаёт содержимое частями; непоместившееся остаётся внутри. Каждый стек сохраняет отдельный `Count` int и NBT, поэтому большой счётчик не обрезается до байта.

`StorageEndpoint` получает актуальную capability при каждой операции. Долгоживущей сильной ссылки на BlockEntity/handler нет. Просмотр и перенос ограничены 256 слотами на вызов; курсоры позволяют добраться до следующих страниц. Короткий кеш просмотра обновляется каждый игровой тик и сбрасывается при наших мутациях/смене capability. Его количества не являются разрешением на commit: реальные операции повторно проверяют содержимое.

Пороговые правила и резерв требуют полного точного подсчёта. Для handlers более 256 слотов они пока безопасно останавливают маршрут; перенос без этих правил продолжает работать по страницам. Это ограничение нужно учитывать при подключении больших сторонних хранилищ.

## Права

Труба запоминает владельца. Чужие трубы не объединяются в одну компоненту, а чужая машина не отдаёт им инвентарь. Настройки, восстановление груза и разрушение проверяют владельца либо оператора. Для двойного сундука проверяются обе половины; выгруженная половина не подгружается автоматикой.

Open Parties and Claims 0.30.1 подключается через его серверный API. Проверено на обычном dedicated server с настоящим JAR: владелец заявил и опустошил тестовую бочку, чужой UUID и автоматика без владельца не получили доступ. Проверка не означает приёмку всех настроек партий, взаимодействий с мобами и разрушения: эти действия проверяются перед соответствующими машинами. Известные неподдержанные providers (`ftbchunks`, `flan`, `griefdefender`, `minecolonies`) останавливают автоматику; универсальная защита любого стороннего плагина не заявляется.

## Проверки

- 28 GameTests и пять JUnit-тестов: точный NBT/симуляция/отказ, фильтры и теги, запас и приоритет, большой handler с доступным 512-м слотом, владельцы, защита ghost-слотов/параметров, восстановление груза после разрушения, базовое ядро.
- Обычный dedicated server: полностью автоматическая цепочка из бочек и труб, 64 меди → 128 эссенций → 64 000 CuE → железо в выходной бочке; оплата 240, остаток 63 760, завершение за 1 087 мировых тиков.
- Клиент: открыто настоящее меню трубы, сервер получил приоритет 20 и пороги 8/16; ghost-шаблон и выбранная грань отображены. Скриншот: `art/previews/item_pipe_menu_ingame.png`.
- Дисковая фикстура сохранила 96 предметов, владельца, фильтр и маршрутизацию при десяти последовательных новых процессах сервера. На десятом перезапуске груз доставлен ровно один раз; каждый запуск прошёл все 28 тестов. Это штатные остановки и настоящие записи/чтения мира, а не десять копирований NBT в памяти.

Повторение базовых проверок: `gradlew.bat --no-daemon build runGameTestServer`. Для OpenPAC: положите свой `open-parties-and-claims-forge-1.20.1-0.30.1.jar` в игнорируемый `.codex-tmp/compat/`, подготовьте собственный `run-opac-server` на loopback и используйте `gradlew.bat --no-daemon -PopacTests runServer`. Нужна строка `CuE OPENPAC CLAIM PASS`; один успешный код Gradle недостаточен. Упрощённый GameTest server для этого provider не используется из-за отсутствующего кеша профилей.

Штатные сохранения и перезапуски не доказывают атомарность внезапного crash между записями разных чанков и произвольного внешнего хранилища. Этот сценарий остаётся открытым D11 и блокирующей частью матрицы 1.0; перенос пока не следует объявлять crash-атомарным.
