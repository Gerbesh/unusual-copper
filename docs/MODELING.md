# Модели и визуальный стиль

Основной редактор проекта — **Blockbench**. Он поддерживает кубоидное моделирование, UV, рисование текстур и анимации. Формат выбирается под рендер конкретного блока, а исходник всегда сохраняется как `.bbmodel`. [Blockbench](https://blockbench.net/), [форматы](https://blockbench.net/wiki/blockbench/formats/).

Blender можно применять для концептов/рендеров или специально согласованной сложной геометрии. MVP не требует Blender. Пиксельные текстуры можно рисовать прямо в Blockbench или во внешнем редакторе.

## Перенос референса в Minecraft

![Референс](references/visual-style.png)

## Форматы и рендер

| Объект/эффект | Путь реализации | Выход |
|---|---|---|
| Статичный корпус/предмет | Blockbench: Java Block/Item | Minecraft model `.json`, PNG, blockstates/item model |
| Соединяемый провод/труба | Статичные части + blockstates/multipart | Корпус и шесть направлений соединения |
| Простая пульсация/пузырьки | Анимированная текстура или событийный клиентский эффект | PNG-кадры + `.png.mcmeta` либо клиентский код |
| Вращение кольца, парящий кристалл | Отдельная динамическая часть в BER | Геометрия, выбранная разработчиком рендера, и Java renderer |
| Сложная костная анимация | GeckoLib-плагин Blockbench после прототипа | `.geo.json`, `.animation.json`, PNG |

Стандартный Java Block/Item JSON не переносит произвольные meshes и костные анимации. Ограничения формата нужно соблюдать в редакторе. Bedrock-экспорт сам по себе не создаёт модель для Forge Java Edition.

BER применяется к динамическому изображению блока, которое не выражается статичной моделью. [Forge: BlockEntityRenderer](https://docs.minecraftforge.net/en/1.20.1/blockentities/ber/). Простые механические движения не требуют автоматически GeckoLib. Если библиотека выбрана, проверяем сборку для **Forge / Minecraft 1.20.1 / GeckoLib 4** и фиксируем точную версию по [инструкции установки](https://github.com/bernie-g/geckolib/wiki/Installation-(Geckolib4)).

Сохранение `.bbmodel` и экспорт — разные действия. У GeckoLib модель, анимация и текстура отдельные, с собственными путями. [Экспорт из Blockbench](https://github.com/bernie-g/geckolib/wiki/Making-Your-Models-(Blockbench)), [Geo Models](https://github.com/bernie-g/geckolib/wiki/Geo-Models-(Geckolib4)).

## Геометрия и текстуры

- Основной блок занимает одну ячейку 16×16×16 единиц моделирования. Большие солнечные панели или высокий кристалл требуют отдельного согласования габаритов, bounds, установки и коллизии до детализации.
- Первую версию каждой машины делать кубоидным блокингом. Болты/царапины/тонкую гравировку преимущественно рисовать текстурой; геометрией менять силуэт.
- Стартовая плотность — около 32 пикселей на ширину блока. 64×64 использовать для согласованных атласов/деталей. Размер атласа не равен плотности: UV соседних моделей должны иметь одинаковый масштаб.
- Исключить наложенные копланарные грани, скрытые внутренние кубы и случайные щели. Проверять повороты, UV, предмет в руке и GUI.
- Предварительный бюджет: обычная машина 20–60 кубоидов, более сложная 60–100, секция трубы до 12. Это ориентир автора проекта; превышение проверяется по необходимости и профилю рендера, а не запрещается движком.
- Настоящую коллизию/selection shape задаёт код. Экспорт внешнего вида не гарантирует правильную физическую форму.

## Стекло, свечение и движение

Начать с корпуса и стеклянного окна. Выбрать cutout для непрозрачного стекла с вырезами или translucent для полупрозрачности; проверить сортировку соседних окон, труб, воды и камеры. Внутренние детали не должны исчезать с обратной стороны.

Бирюзовая текстура сама по себе не светится. Для видимого в темноте ядра нужен согласованный emissive/fullbright слой или рендер; динамический свет на окружение — отдельная возможность, не требование MVP. Видимые кадры пузырьков можно сделать текстурой: это не физическая жидкость и не транспорт сущностей.

Состояния: `idle`, `working`, `paused`, `unpowered`; импульс `operation_complete` при завершении. Длительность визуального эффекта не определяет игровой результат. Частицы суммировать по событиям, ограничивать расстоянием/настройками; не создавать серверные сущности ради декоративных кристаллов или пузырьков.

| M2 | `calibration_wand`, `face_selector`, `aura_cultivator`, `magnetic_collector` | Инструменты, линза к земле, магнитная катушка |

## Организация файлов после появления MDK

```text
art/blockbench/<asset_id>.bbmodel
art/textures/<asset_id>.png                  # мастер-текстура, если редактируется отдельно
art/previews/<asset_id>_ingame.png
src/main/resources/assets/unusualcopper/
  blockstates/<block_id>.json
  models/block/<block_id>.json
  models/item/<item_id>.json
  textures/block/<asset_id>.png
  textures/item/<asset_id>.png
  geo/<asset_id>.geo.json                    # только при выборе GeckoLib
  animations/<asset_id>.animation.json       # только при выборе GeckoLib
```

ID: lowercase `snake_case`, namespace `unusualcopper`; относительные ссылки ресурсов без абсолютных путей художника. Папки runtime здесь показаны как план, экспортов пока нет. Исходники, PNG и экспорт обновляются в одном PR.

## Приёмка модели

1. `.bbmodel` открывается, PNG и экспорт находятся в репозитории, пути ресурсов валидны.
2. Машина узнаваема с 8–16 блоков; вход/выход и состояние различимы. Проверены установка, поворот, все стороны, инвентарь и рука.
3. Нет UV-ошибок, z-fighting и неожиданной прозрачности днём, ночью, у воды и соседних труб.
4. На низких настройках частиц GUI всё равно объясняет состояние; обычный клиент без shaders отображает модель корректно.
5. Сохранены скриншоты из игры. Для динамической части — видео/последовательность кадров и замер тестовой сцены с 50–100 машинами.
6. Модель использует общий масштаб/палитру; авторство и происхождение материалов записаны. Концепт не используется как готовая текстура.
